# EP-02.01 — Durable PostgreSQL task queue

## Scope and acceptance

Trace: F-10; E-03/E-05; P-11/P-15/P-21; ADR-002/003/013. Add a reviewed migration,
immutable task inputs/retry policy, dependency-aware queue, fenced leases, bounded
retry, waiting-user isolation, cancellation, event history and crash-safe reclaim.
Only dedicated ACOA application connections may use the adapter. No provider,
browser, email, model, scheduler daemon or external-action executor is activated.

## Execution and recovery

The caller supplies a SQLAlchemy `Connection` inside an explicit transaction;
the adapter never creates a connection, reads credentials or commits. The caller
must commit a claim before dispatching work and roll back any failed operation.
State and events commit together. PostgreSQL time controls due dates and leases.
`FOR UPDATE SKIP LOCKED` serializes competing claims without waiting on a task
already claimed in another transaction. Each attempt gets a fresh UUID fence;
owner, token and live deadline are required for worker changes. Row locks also
serialize cancellation and recovery against workers. Heartbeats cannot shorten
or resurrect an expired lease. Task cancellation fences work but cannot undo an
external side effect; external work must use the later executor protocol.

Automatic replay defaults to `never`. Only a conservative read/planning task
allowlist accepts `safe`, and handlers must still recheck authorization, budget
and idempotency before work. External execution is never replay-safe. A transient
safe failure retries with capped exponential backoff and a finite attempt count.
Expired unsafe work and ambiguous external outcomes become `blocked`, requiring
reconciliation. Retry exhaustion becomes `failed`. Raw exceptions are not stored.

`waiting_user` stores an exact question UUID and releases the lease. An approved
answer adapter must authenticate the user, resolve an approved answer and supply
its evidence reference when resuming that exact question. UUIDs alone do not prove
approval. Resume starts a new bounded retry phase while preserving the total
attempt count and original immutable retry specification. Independent tasks keep
running; dependent tasks require all predecessors completed. Dependencies can
only be declared on initial enqueue, referencing existing tasks; the supported
adapter cannot introduce cycles by later edits.

Task bodies are opaque input references, not arbitrary commands or embedded PII.
The app role may append/read task events but cannot update/delete them. This is
not tamper resistance against a migration administrator or arbitrary compromised
application SQL; the trusted application boundary remains required. Downgrade
refuses destructive removal of retained history.

## Verification — 2026-10-15

- Applied `0001_task_queue` using the validated migration role on the dedicated
  local ACOA database. Repeated upgrade/current verified the head.
- Direct PostgreSQL runtime probe passed: exact enqueue idempotency, conflicting
  task identity rejection, dependency blocking/unblocking, running/heartbeat,
  wrong-owner and expired/stale fence rejection, waiting-user isolation, wrong
  question rejection, exact resume, unchanged retry specification, delayed safe
  recovery, exhausted retry and unsafe external replay blocking. This probe's
  entire transaction was rolled back.
- Two simultaneously open transactions claimed distinct tasks; neither could
  obtain a task locked by the other. Only the ACOA PostgreSQL container was
  restarted. Committed leases persisted, expired leases were recovered and new
  attempts received fresh fences. Cancellation fenced the old worker. Synthetic
  committed rows/events were removed by exact UUID using the migration role;
  the development queue was verified empty afterward.
- App-role event update/delete, schema DDL and migration metadata access were
  rejected. The queue adapter rejected migration-role connections.

All 98 existing tests passed on Windows; Ruff lint/format, strict mypy for source
and all migration modules, Actionlint and final diff checks passed. Migration
execution was verified in the Linux maintenance container. The new queue's
Python runtime was exercised on Windows; no Linux queue-worker check is claimed.
The service was returned to the base internal network without a published port.
There are no new test/fixture files. A long-running worker, user-answer adapter,
application ledger and reconciliation provider are later tasks, not implied by
these direct queue checks. Process-kill and provider-timeout fault injection remain
EP-02.05 scope; database restart was actually exercised here.
