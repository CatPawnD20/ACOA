# EP-10.04 — Fail-closed activation readiness

## Scope and requirement links

This task implements the complete pre-activation configuration check required by
`E-04`, `E-07`, `E-08`, `E-11`, `P-04`, `P-10`, `P-17`, `P-20`, `P-21`,
`ADR-006`, `ADR-011` and `ADR-013`. It validates configuration evidence without
collecting real values, enabling a provider, running a pilot or authorizing production.

## Delivered behavior

- Readiness binds the exact active approved profile and nonempty current goals to local
  SHA-256 evidence. Stored audit payloads contain identities, versions and hashes rather
  than profile values.
- Current Policy Authority must contain an active approved grant. Both the grant identity
  and its exact limit-policy identity must match configuration, closing the previous gap
  between an approved quota policy and the configured limits used by the Policy Gate.
- Application, outreach, money, token and time limits must be positive and explicit;
  weekly application capacity cannot be below daily capacity, monthly money cannot be
  below daily money, and currency must be declared.
- Every granted channel and account needs a current terms-evidence binding. Extra channel
  or account bindings, uncovered data categories, unknown/duplicate category declarations
  and missing authorized email configuration fail closed.
- `ready_for_pilot` still requires `dry_run=true` and
  `external_actions_enabled=false`. The assessment cannot activate external actions.
- The repository locks current Policy Authority, recomputes the complete assessment and
  stores an exact-idempotent, append-only audit record for the application role.

## Verification

Verified locally on 2026-10-17:

- A synthetic complete profile, goals, approved grant, matched limit policy, channel terms
  binding and bounded quotas/budgets produced `ready_for_pilot` while external actions
  remained disabled. Safe defaults with missing inputs produced structured blockers.
- Migration graph/history and offline SQL selected one head at
  `0027_activation_readiness`; the revision was applied to the dedicated development DB.
- An application-role PostgreSQL probe recomputed the current blocked assessment under the
  authority lock, verified exact idempotency and select/insert-only permissions, and
  rolled the probe transaction back.
- A separate current-state assessment was committed locally. It reports missing profile,
  goals, grant, quota and budget declarations without recording any personal value.
- Existing tests, Ruff, strict mypy, dependency consistency, Compose, approved documents,
  image/source identity and active checksums are included in the final gate. No test,
  fixture, mock or testing utility was added or modified.

## Current gate and remaining boundary

The implementation is complete, but the current installation is intentionally `blocked`:
no real profile, goals, grant, channel terms binding, quota or budget configuration exists.
Supplying those inputs is a privacy- and authorization-sensitive user step. EP-10.05 cannot
run a live pilot until this assessment becomes `ready_for_pilot` and the user separately
authorizes the controlled test target. EP-10.06 retains explicit production activation.
