# EP-00.04 — CI and Security Checks

## Objective and authorized boundaries

Connect existing unit/import checks, Ruff, strict mypy, dependency consistency,
known-vulnerability auditing, and Git-history secret scanning to GitHub Actions.
Trace: L4 EP-00.04; E-07/E-09/E-10; P-17; ADR-001/011.

The user authorized continuation on 2026-10-14. No remote repository, push,
workflow dispatch, cloud deployment, production credentials, or real employer
action is included. Existing tests remain unchanged; no new tests, fixtures,
mocks, or test utilities are added. Python package dependencies remain unchanged.

## Work units and acceptance

1. Inspect the existing commands and create a workflow running Python 3.12.14 on
   Ubuntu 24.04 and Windows 2022. Pin external actions by full commit SHA, grant
   only repository read permission, and disable persisted checkout credentials.
2. Audit the installed dependency inventory, including development and build
   tooling, with pip-audit in a separate environment. Fail on advisories or audit
   collection errors; do not auto-fix or suppress vulnerability IDs.
3. Scan complete checked-out Git history with a checksum-verified Gitleaks binary.
   Redact values, fail on findings/errors, and honor no inline allow comments.
4. Validate workflow syntax with actionlint. Exercise the existing commands on
   Windows and in a clean Linux container holding only exported tracked source,
   never the actual workspace's private files or secret directory. Review the
   staged diff and checksums before a focused local commit.

## Design and limits

The workflow uses `push` to `main`, `pull_request`, and explicit manual dispatch.
It has no deployment or artifact-upload step, no provider secrets, and no database
or external-application service. Untrusted PR code receives no write token or
production credentials. `pull_request_target` is not used.

The quality job explicitly installs the project build requirements from
`pyproject.toml` and the backend's editable-build requirement hook to include those
packages in the audited inventory. Pip retains its normal build isolation when
installing packages from source. Mypy is installed from source for compatibility with this
workstation's Windows Application Control. Direct tools are pinned; transitive
dependencies remain resolved by pip rather than a claimed complete lockfile.

pip-audit 2.10.1 audits public package names and exact installed versions via the
PyPI advisory API. It does not upload source files, environment configuration,
personal data, or credentials. The local unpublished `acoa` distribution is
excluded; all other installed quality-environment distributions are included.
The scanner's separate own tool environment and temporary dependency-build
environments are not part of that inventory.
Unavailable advisory services fail the job. Audit results describe known Python
package vulnerabilities at scan time, not all possible code or container risks.

Gitleaks 8.29.1 is selected after a matching token detection was verified locally;
the newer 8.30.1 has a reported false-negative issue. The workflow pins the Linux
archive SHA-256 from the official release checksums. Historical documentation and
source are scanned without broad exclusions or an allowlist. Ignored local files
are not in Git history and must still remain untracked. Gitleaks is heuristic and
does not guarantee the absence of every kind of secret.

Official references: [checkout](https://github.com/actions/checkout),
[setup-python](https://github.com/actions/setup-python),
[pip-audit](https://github.com/pypa/pip-audit),
[Gitleaks](https://github.com/gitleaks/gitleaks),
[Gitleaks 8.30.1 report](https://github.com/gitleaks/gitleaks/issues/2170),
and [actionlint](https://github.com/rhysd/actionlint).

G0 is not declared fully complete here: the approved L4 gate also requires
migration infrastructure. EP-00.03 provides separated DB roles/schema ownership
but no Alembic runner; that missing bootstrap prerequisite must be addressed in
a separate focused task before G0 is closed. Business schema migrations remain
EP-02 scope. Approved L0–L4 documents are not edited.

## Verification results

Verified locally on 2026-10-14:

- Workflow syntax and built-in Actions checks: actionlint 1.7.12 passed. Its
  optional ShellCheck/Pyflakes integrations were disabled; shell operations were
  exercised directly as described below.
- Windows: final editable installation succeeded; pip consistency, **98 existing
  tests**, Ruff check/format, and strict mypy (four existing files plus the
  preparation script separately) passed. The installed public-package inventory
  including Hatchling/editables passed pip-audit with no known vulnerabilities.
- Clean Linux amd64: used the digest-pinned official Python 3.12.14 slim-bookworm
  image with only exported tracked source mounted read-only, no workspace secrets,
  no database mount, all capabilities dropped, and no-new-privileges. Fresh source
  installation, pip consistency, **98 existing tests**, Ruff check/format, strict
  mypy, and the installed-dependency audit passed. The temporary container was
  removed by `--rm`.
- Linux Gitleaks release download/checksum/extraction and exported-source scan:
  passed with `--no-same-owner` extraction under the restricted container. The
  local slim image used Python's HTTPS downloader for the same official archive;
  the workflow uses curl on the hosted Ubuntu runner. Both Windows and Linux
  downloaded archives matched their official SHA-256 values.
- Git history secret scan: all three pre-existing local commits passed. Staged
  source is also scanned before commit. A generated, never-persisted synthetic
  token was correctly rejected with exit code 1 and fully redacted output. No real
  secret was used as a probe.
- Dependency failure behavior: the initial Windows inventory's pip 25.0.1 produced
  a failing audit with known advisories. Updating only the project-local pip to
  the workflow's 26.2.1 and including the build packages produced a clean audit.
  No vulnerability ignore list or automatic fix flag was added.

Fresh-install attempts exposed missing editable/source-build requirements when
build isolation was disabled. The final workflow keeps pip's normal build
isolation and explicitly installs the project build tooling for audit visibility.
A sandbox DNS limitation during one Windows install was resolved by using the
authorized network-access execution path. None of these failed attempts were
reported as passes or handled by changing Windows security policy.

No GitHub remote or hosted Actions run exists for this task. Actual runner image
behavior, GitHub token enforcement, checkout/setup action execution, and branch
protection were not exercised. Passing local command equivalents and actionlint
does not claim a hosted run has succeeded. Future remote activation remains a
separate user-authorized action. G0's missing migration runner remained outstanding
at the time of this task. The subsequent [migration follow-up](EP-00.03-migration-runner.md)
supplies that prerequisite and extends the workflow with migration tooling/offline
checks; see its newer verification record.
