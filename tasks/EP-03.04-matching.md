# EP-03.04 — Hard exclusions and multi-criteria matching

Trace: F-01.06, F-05.01–07; E-03.03/E-05.07/E-06.02; P-03; ADR-004/015.

## Scope and behavior

Matching now has two explicit phases. The deterministic first phase evaluates each
user hard condition against a versioned opportunity attribute with evidence status.
A confirmed required value that is absent, or a confirmed excluded value that is
present, returns `excluded` immediately. Missing or conflicting hard evidence returns
`research_required`. Neither path evaluates preference scores, so a high model or
preference score cannot compensate for a hard failure or unknown mandatory fact.

Only opportunities that pass all hard conditions reach multi-criteria evaluation.
The policy must explicitly weight target alignment, opportunity value, freshness,
cost efficiency and certainty. It also names required criteria, fit and low-priority
thresholds, minimum required-criterion score and assessment lifetime; there are no
production defaults. Signals bind evidence IDs and may reference only verified facts
from the exact active profile variant. Conflicts or missing required signals produce
research rather than optimistic fit. The aggregate is retained as an exact rational
number, avoiding ambient Decimal rounding changes, but it is never the sole gate.

Every result binds assessment ID, profile variant/version, goals ID/version,
opportunity ID/version/content hash, policy version, evaluation time and expiry.
Reuse requires all bindings and validity windows to remain current. The immutable
record includes structured hard outcomes and individual criterion signals so missing
information and each criterion's influence remain inspectable.

Migrations `0008_match_assessments` and `0009_match_assessment_grants` add immutable
assessment storage with explicit application `SELECT`/`INSERT` access. Application
`UPDATE`/`DELETE` remains denied. Recording uses insert-on-conflict plus exact readback,
which provides idempotency without requiring update permission. The follow-up grant
revision was added after the retained development volume exposed that `SELECT FOR
UPDATE` would incorrectly require broader table privileges; the applied `0008` file
was not rewritten.

## Observed local verification

- Existing baseline and static checks were run without adding or modifying tests,
  fixtures, mocks or test utilities. Focused checks used transient synthetic values.
- A confirmed excluded country stopped before scoring despite all five preference
  signals being high. An unknown mandatory country returned research with no score.
- Passing hard conditions produced fit only when the aggregate and every required
  criterion met their independent thresholds. A weak required freshness signal was
  low priority; a borderline aggregate and a conflicted criterion required research.
- A signal referencing a fact outside the exact approved profile snapshot was
  rejected. Profile, goal, opportunity, policy and expiry changes made reuse stale.
- Exact aggregate numerator/denominator remained identical under multiple ambient
  Decimal precisions.
- PostgreSQL reached `0009_match_assessment_grants`. Insert and exact repeated record
  were idempotent; reuse of an assessment ID with changed content was rejected;
  direct application-role update was denied. The synthetic transaction rolled back.

## Remaining boundaries

Opportunity normalization/source ingestion and a trusted signal-producing evaluator
are not implemented here. Evidence UUIDs and hashes are bindings, not authentication.
The thresholds and weights exercised were synthetic; production values remain unset
until EP-03.05 evaluates labeled examples. No result authorizes an application,
message or other external action. There is no real profile, opportunity, model call,
provider integration or employer target in this verification. Hosted CI has not run
because no remote repository exists.
