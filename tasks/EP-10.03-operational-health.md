# EP-10.03 — Operational health and safe shutdown

## Scope and requirement links

This task implements the bounded failure response required by `E-04.06`, `E-11.05`,
`P-21`, scenarios `S-39`/`S-40`, and `ADR-003`/`ADR-011`. It does not add a service
process, notification transport, live provider, production deployment or external action.

## Delivered behavior

- Typed health observations identify one dependency and retain a sourced evidence hash.
  Deterministic assessment accepts only observations inside an explicit time window and
  applies a positive failure budget.
- Healthy, degraded, locally unavailable and systemic states map respectively to continue,
  alert, dependency isolation and global safe mode. Any systemic observation wins over a
  later healthy observation in the same window.
- The repository recomputes each assessment from its exact evidence before writing it.
  Observation and assessment identities are exact-idempotent, while retained records and
  pending alerts are append-only for the application role.
- Systemic risk updates Policy Authority to `paused=true`, `dry_run=true` and
  `external_actions_enabled=false` in the same caller-owned transaction as its assessment
  and critical alert. Local dependency isolation leaves global authority unchanged.
- Graceful shutdown releases an owned fenced lease with the structured `lease_expired`
  class. Existing task policy retries bounded replay-safe work and blocks non-replayable
  external-action work rather than risking a duplicate effect.

- A direct behavior probe covered continue, warning, dependency isolation and systemic
  safe-mode decisions, plus replay-safe retry and risky-task blocking on shutdown.
- Migration graph/history and offline SQL generation selected one head at
  `0026_operational_health`; the revision was applied to the dedicated development database.
- An application-role PostgreSQL probe recorded and deduplicated a local isolation without
  changing authority, then atomically entered systemic safe mode and created the second
  alert. Rolling back restored the original authority and alert count.
- The probe confirmed select/insert access and denied update/delete privileges on retained
  alert records. It used synthetic identifiers/hashes and performed no external action.
- The final repository gate covers the existing test suite, Ruff formatting/linting,
  strict mypy, dependency consistency, Compose rendering, approved-document preservation,
  image/source identity and the active checksum manifest. No test, fixture, mock or testing
  utility was added or modified.

## Remaining boundaries

No continuously running API, scheduler or worker exists yet, so health polling, process
signal registration and notification delivery are not wired to a daemon. Pending alerts
remain for a later authorized adapter. EP-10.04 must validate real user configuration;
EP-10.05–06 retain the pilot and explicit production-activation gates. Real external
actions remain disabled.
