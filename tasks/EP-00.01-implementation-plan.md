# EP-00.01 Implementation Plan

Status: approved, implemented, and verified on 2026-10-14, including local Git preparation. Routine work within the user's authorized scope does not require repeated approval; critical security/privacy/authorization concerns require a user decision.

The subtasks below preserve the approved implementation plan and its pre-implementation assumptions. The actual tool selection, environment adjustments, and successful checks are recorded in [the verification record](EP-00.01-verification.md).

## Goal and inputs

Implement only the [bootstrap task](EP-00.01-bootstrap.md): a minimal installable `src`-layout Python package, focused development tooling, safe import smoke tests, and reproducible local instructions. Inputs are the [canonical specifications](../docs/README.md), existing AGENTS rules, and the [workspace audit](../docs/workspace-audit.md).

Completion means installation succeeds in a clean development environment, package import has no operational side effects, smoke tests and configured static checks pass, and the reviewed changes contain no credentials or personal data.

Primary trace: L4 sections 12.1–12.2; K-01; E-09.01/E-09.06; E-10.01/E-10.03/E-10.07; E-07.03; ADR-001. F-08.01, P-01/P-02/P-17, and ADR-006/007 define prohibited bootstrap side effects, not features implemented by this task. ADR-015 remains a future integration boundary.

## Subtask 1 — Packaging and toolchain

- **Objective:** declare one minimal, installable Python project and compatible developer tools.
- **Files:** create `pyproject.toml`; choose a build backend; configure pytest, a linter/formatter, and the narrow type-checking scope required by L4 EP-00.01. Record exact supported Python/tool versions in README in subtask 4.
- **Dependencies:** implementation-plan approval and read-only inspection of available Python runtimes. Verify supported versions and dependency compatibility before finalizing metadata; no Python or package version has been selected or validated during workspace preparation.
- **Boundary:** no runtime integration dependencies. Proposed tooling is pytest, Ruff, and mypy; verify this selection before installation. No workflow engine, web framework, provider SDK, database driver, or browser package.
- **Acceptance:** a fresh isolated environment resolves the declared development dependencies; editable installation succeeds and project metadata names `acoa` with a `src` layout.
- **Checks:** install with `python -m pip install -e ".[dev]"`; inspect installed package metadata and dependency results. Installation may download dependencies; application smoke tests may not access the network.
- **Security:** use only development resources without production secrets; review dependency provenance. No `.env` or credential discovery.
- **Trace:** ADR-001; E-10.03/E-10.07; L4 EP-00.01.

## Subtask 2 — Side-effect-free package

- **Objective:** make `acoa` importable without starting any operation.
- **Files:** create `src/acoa/__init__.py` only, with minimal package content.
- **Dependencies:** subtask 1 establishes the package layout.
- **Boundary:** no settings module, startup runner, CLI, domain placeholders, scheduler, provider interface, business logic, or external action entry point. Configuration validation belongs to EP-00.02.
- **Acceptance:** import succeeds in the isolated environment with no `.env`, database, credentials, network access, worker, browser, or background job.
- **Checks:** isolated import smoke verification from outside the repository working directory, ensuring the installed package is used.
- **Security:** zero live integration calls and no import-time reading of private files; `dry_run=true` / `external_actions_enabled=false` remain documented requirements, not a prematurely implemented settings system.
- **Trace:** K-01; ADR-001; E-09.01; E-10.03; L4 section 12.2.

## Subtask 3 — Focused smoke tests and privacy exclusions

- **Objective:** verify installation/import invariants and keep private/local artifacts out of future Git tracking.
- **Files:** create `tests/test_package_smoke.py` and `.gitignore`. Configure test paths in `pyproject.toml` as needed.
- **Dependencies:** subtasks 1–2. Smoke tests are explicitly part of this proposed task; no tests are created before approval.
- **Boundary:** only import/package invariants. No policy engine tests, database tests, generated fake provider modules, reusable testing infrastructure, or external services. Provider fakes are unnecessary when no provider is implemented.
- **Acceptance:** package import and metadata checks pass; imports are exercised under guards that fail if network connections, subprocesses, or background threads are started. Missing `.env` and credentials do not prevent import. Git exclusion patterns cover local environments, real credentials/tokens, private CV/application data, browser profiles, DB volumes, caches, logs, and build output while retaining legitimate source and test paths.
- **Checks:** run `python -m pytest -q`. Check `.gitignore` against harmless path names without creating real secret/personal files; use `git check-ignore` only if a local Git repository has been initialized with authorization. In the uninitialized workspace, report that Git integration verification is pending rather than claiming tracking protection was exercised.
- **Security:** use only synthetic names and local inputs. Guards must fail rather than permit an attempted external effect. `.gitignore` is an accidental-tracking safeguard, not a replacement for reviewing staged files.
- **Trace:** E-09.01; E-07.03; E-10.01/E-10.07; P-17; F-08.01 as a scope boundary; L4 section 12.2.

## Risks and deferred decisions

- Tool availability, supported Python versions, and package compatibility are not yet verified. Resolve these during subtask 1 without inventing a supported version.
- Dependency installation can require network access. Missing network/package availability is a verification limitation, not a reason to skip smoke behavior or silently install into a global environment.
- Git initialization is not part of this approved preparation. Remote GitHub creation and push require explicit authorization; bootstrap packaging itself can be verified locally without a remote.
- Existing Git `core.autocrlf=true` may affect raw document hashes after future checkout. Address the line-ending policy explicitly before Git onboarding; preserve approved bytes during this task.
- Document-internal historical status/reference inconsistencies remain recorded in the specification index. They are not missing policy approval and do not authorize edits to approved documents.
