# EP-06.05 — Important reply notifications and mail daily digests

## Scope and requirement links

This task implements the mail-specific notification and reporting boundary for
`F-09.01`, `F-09.02`, `F-09.05`, `F-11.07`, `E-04`, `E-07`, `E-08`, `P-09`, `P-12`,
`ADR-009` and `ADR-014`. It uses only synthetic identifiers and classifications. No
message body, real mailbox, notification service or recipient was accessed.

## Delivered behavior

- Reply classifications cover positive, negative, information request, interview
  request, automatic reply, ambiguous and opt-out outcomes. The record binds a protected
  message snapshot hash and explicit relation evidence; mail content remains untrusted.
- PostgreSQL accepts a classification only when the exact mailbox event belongs to the
  account/provider/message/thread and that thread has a sent record no later than the
  same application. Subject or company-name similarity cannot create the relationship.
- Positive, information-request, interview-request, ambiguous and opt-out classifications
  deterministically create immediate pending notification items. Negative and automatic
  replies remain available for the daily digest. Importance is not supplied by an agent.
- A unique event-derived key and immutable classification identity prevent replayed mail
  events from creating a second notification. This boundary records notification intent;
  it has no delivery transport.
- Explicit closed reporting windows produce immutable mail digests with incoming,
  classified, immediate-notification, reply-draft and follow-up-draft counts. Empty
  windows are valid reports. No schedule, timezone or delivery channel is invented while
  those user preferences remain TBD.

## Verification

Verified locally on 2026-10-16 with synthetic PostgreSQL records:

- Migration `0020_mail_notifications` was applied to the internal-only PostgreSQL
  service. A transaction probe connected a sent thread to two mailbox events, recorded
  an interview request twice and an automatic reply once, and observed exactly two
  classifications and one notification.
- The same probe rejected an unrelated application/thread, generated a populated digest
  and a zero-result digest, and confirmed that the application role cannot update or
  delete notification items. The transient probe was removed afterward.
- The final gate covered 98 existing tests, Ruff lint/formatting, strict mypy, package
  consistency, migration graph/offline SQL, approved-document preservation and the
  active checksum manifest. No test, fixture, mock or testing utility was changed.

## Remaining boundaries

An authenticated message-fetch/classification adapter must create the protected snapshot
and relation evidence before this repository accepts real data. Notification delivery,
delivery/read state updates, user channel preferences, quiet hours and scheduling belong
to later scheduler/dashboard work. A pending notification item does not mean the user
received or read it.
