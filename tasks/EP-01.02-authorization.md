# EP-01.02 — Authorization and Separate Sensitive Consent

## Scope and acceptance

Implement immutable, finite authorization declarations and separate sensitive-data
consent. Trace: EP-01.02; F-01/F-12; E-07; P-01/P-02/P-17/P-18; ADR-006.

1. Model explicit action/channel/recipient/account/data-category scopes, a limit
   policy reference, policy/content versions, validity windows and user approval.
   No wildcards, coerced enums, duplicate scopes or unbounded validity.
2. Bind approval to exact content and version; changes cannot retain an old review.
   Expired, revoked, unapproved and future-dated approvals cannot be active.
3. Require separate consent for sensitive categories, bound to one exact parent
   grant and its content. General profile approval is not sharing permission.
4. Represent the approved permission modes without granting arbitrary action rights.
   The next Policy Gate task applies the binding L2/L3 action matrix.
5. Reuse shared human-review validation and hashing without changing the existing
   `acoa.domain.profile.UserReview` / `ReviewDecision` import paths.

## Trust and boundaries

These objects are declarations, not proof of authenticated origin. A model output,
UUID or hash cannot confer authority. The future trusted input adapter and
PostgreSQL grant resolver must authenticate and persist actual user decisions,
load the authoritative latest version, and recheck revocation at execution time.
Grant/consent approval here activates no provider or integration.

The data-category vocabulary is closed and deliberately includes a catch-all
`other_sensitive_document` category. Unknown categories fail closed. Artifact
classification must be supplied by trusted validation, not by an agent claiming
that sensitive contents are an ordinary CV. Actual PII detection/classification,
real account ownership, recipient evidence, quota/budget consumption and action
reservation belong to their later owners; scopes alone do not verify them.

`limit_policy_id` identifies a later immutable persisted policy record. No numeric
limit is invented. Modeled grant actions may include forbidden action classes;
the fixed Policy Gate must still return user-only/user-sends/deny regardless of
what a grant declares. No real grant or personal data is populated.

## Verification

Direct synthetic runtime checks passed: unapproved grants are inactive, exact
approval activates only the declared window, expiry is exclusive, revocation
advances the version/removes approval, changed account/data/recipient scope cannot
reuse a review, coerced enum and mutable wildcard scope are rejected, and sensitive
consent requires a separate review tied to the exact parent grant. Consent expiry,
revocation, stale parent and uncovered categories fail closed. Legacy profile
review imports remain compatible. Ruff and strict mypy passed; no new test files,
fixtures or dependencies were added.

Existing checks and profile-review regression probes are run before commit. All
inputs were synthetic. Authenticated ingestion, persistent grant lookup and real
external sending were not exercised or implemented.
