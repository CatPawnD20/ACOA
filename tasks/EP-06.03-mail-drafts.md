# EP-06.03 — Policy-bound draft-only mail

## Scope and requirement links

This task implements initial-application mail preparation, reply drafts and follow-up
drafts for `F-09.03`, `F-09.04`, `F-09.07`, `E-04`, `E-07`, `P-01`, `P-02`, `P-09`,
`ADR-006`, `ADR-007` and `ADR-014`. It remains offline: only synthetic addresses,
content and opaque identifiers were used. No OAuth token, mailbox or real recipient was
accessed, and no message was sent.

## Delivered behavior

- A mail-draft record binds one open application, one opaque account, one opaque
  recipient, the exact account address, recipient address, subject, body and thread,
  and the exact policy action. Private addresses and content stay out of dataclass
  representations.
- Initial-application drafts carry `submit_initial_application` intent for a fresh
  Policy Gate evaluation before any later send attempt. Preparing the draft itself does
  not grant execution authority or count as submission evidence.
- Reply and follow-up drafts accept only `draft_reply` and `draft_followup`, require an
  exact source message/thread and a trusted matching communication purpose, and persist
  only after Policy Gate returns `ALLOW` with `DRAFT_ONLY`.
- `send_reply` and `send_followup` remain `USER_SENDS` actions. The Policy Gate blocks
  both even when safe-mode configuration is made permissive; there is no provider send
  method or application-level sent transition.
- PostgreSQL stores immutable draft records separately from immutable provider-draft
  receipts. Neither table has a sent or delivered state, and the application role has
  read/insert-only access. Exact replay is idempotent; changed content under an existing
  draft identity is rejected.

## Verification

Verified locally on 2026-10-16 with synthetic content and no real mailbox:

- A transient offline probe exercised initial, reply and follow-up preparation, exact
  content/action binding, rejected a send action disguised as a draft, and confirmed
  `send_reply`/`send_followup` block with `USER_SENDS`. The probe was removed afterward.
- Migration `0018_mail_drafts` was applied to the dedicated internal-only PostgreSQL
  service. A transaction probe recorded all three draft kinds, an idempotent fake
  provider receipt and an exact replay; it rejected changed content and confirmed that
  the application role cannot update or delete retained drafts. The probe was removed.
- The final gate covered the existing test suite, Ruff lint/formatting, strict mypy,
  package consistency, migration graph/offline SQL, approved-document preservation,
  local links and the active checksum manifest. No test, fixture, mock or testing
  utility was added or modified.

## Remaining boundaries

EP-06.04 owns controlled test-mailbox sending, timeout classification, sent-message
evidence and thread reconciliation. A successful provider draft receipt proves only
that a remote draft exists; it does not prove sending, delivery or reading. An uncertain
live provider draft creation must be reconciled before retry, so blind live retries and
real OAuth activation remain disabled.
