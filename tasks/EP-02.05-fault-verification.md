# EP-02.05 — Concurrent workers, process termination and lost-response verification

## Scope and environment

Trace: F-08/F-10; E-03/E-04/E-05; P-11/P-15/P-21; ADR-002/003/007/013.
Exercise the completed queue/ledger/executor/reconciliation flow under actual
process termination, competing transactions, simulated provider timeout, lost
local response persistence and dedicated database restart. Source under exercise:
`ad4eaf1`; PostgreSQL migration head `0004_reconciliation`; Python 3.12.14 on
Windows, dedicated PostgreSQL 18.6 in Docker. No production provider or real data.

No source change was needed by this fault exercise. Per user instructions, no
tests, fixtures, mocks or verification-utility files were added. The harness ran
inline; its synthetic providers existed only in the verification process. The
98 persisted baseline tests are bootstrap/configuration checks, not a claim that
these new fault cases are automated in CI.

## Acceptance results — 2026-10-15

| Fault/condition | Observed result |
|---|---|
| Separate queue worker killed after committing claim/start | Running task and lease persisted. After expiry, only replay-safe work became retry-scheduled; new worker got a fresh fence and completed attempt 2. |
| Two concurrent connections reserve different initial applications with one-slot quota | Exactly one became reserved; the other was blocked. No overbooking. |
| External worker killed after committing dispatch, before provider invocation | Executing record persisted. Deadline recovery produced unconfirmed/review; repeated executor call invoked no provider. |
| Synthetic provider performs its counted effect then raises timeout | Unconfirmed result and incident; repeated executor call kept provider invocation count at one. |
| Provider acknowledges but local response persistence raises | Executing record survived; retry did not call the provider again. Deadline recovery subsequently marked unconfirmed. |
| Dedicated PostgreSQL restart with those operations retained | Three unconfirmed operations, all three money holds and completed queue task survived. Repeated execution still did not call the provider again. |

Workers were real independently launched Python processes using the exact base
interpreter, isolated mode/no site initialization and explicit repository/package
paths. They inherited only Windows system-root variables. Credentials came only
from the explicitly selected generated development password file, never from
CLI arguments, inherited production tokens or `.env`. Each worker signaled only
after its transaction committed; the harness terminated only its own process and
waited for exit. It did not kill another application or change OS security policy.

The counted synthetic provider effect proves local one-invocation behavior; it
does not prove exactly-once behavior at an external employer/provider. A killed
worker that did not actually invoke its provider was still treated as uncertain,
which is the intended conservative recovery rule.

## Preservation and limits

The probe required an empty dedicated development task/action queue and safe
current authority before setup. All targets/accounts were synthetic `.invalid`
records. Before cleanup, current authority was disabled and its grant removed.
Cleanup used only generated task/owner/attempt/request identifiers under the
migration role; no volume reset, schema drop, unrelated database/container or
unscoped data deletion occurred. Full safe authority defaults were restored and
no active action records remained. Synthetic authority-change history was kept.

This completes the local EP-02 safety gate with runtime evidence for durable
recovery and no blind automatic second submission. It is not release approval:
actual identity/permission ingestion, real provider limits/verification, protected
source artifacts, notification delivery, operating-system sandboxing and hosted CI
remain their later gates. The new fault cases are recorded here and in the session;
there is no persistent fault-regression suite without an explicit request to add it.

All 98 existing baseline tests, Ruff lint/format, strict source/deployment/migration
mypy and diff checks passed. PostgreSQL was restored to the base internal network
with no published host port. No source change followed the exercised commit.
