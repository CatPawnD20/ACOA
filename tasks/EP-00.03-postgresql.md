# EP-00.03 — Dedicated PostgreSQL Deployment

## Objective and scope

Provide a portable Compose definition for a dedicated ACOA PostgreSQL service,
private network, persistent volume, file-mounted passwords, and separate admin,
migration, and application roles. Trace: L4 EP-00.03; E-05/E-07/E-11;
ADR-002/011/013. Routine implementation is authorized by the user's instruction
to continue on 2026-10-14.

Application schemas, application database adapters, Alembic revisions, APIs,
workers, cloud deployment, and real employer actions remain outside this task.
The existing safe configuration defaults remain unchanged.

## Work units and acceptance criteria

1. Add Compose and optional loopback-only host access. Use the same pinned
   PostgreSQL image on local/cloud Docker, with project-scoped resources and no
   shared database service. Validate the configuration and resource ownership.
2. Generate separate random development passwords in ignored local files without
   reading, printing, or overwriting existing credentials. Verify repeated setup
   preserves files. Document Windows filesystem permission limitations.
3. Initialize least-privilege roles and an empty application schema on a fresh
   volume. Authenticate with the app and migration roles, verify SQL access and
   forbidden DDL/admin actions, and verify migration-created objects are accessible
   to the application through default grants.
4. Restart only the new ACOA service and verify persistence. Run existing Python
   checks, inspect the diff, update documentation/checksums, and make a focused
   local commit. Do not change approved specification bytes or other containers.

## Risks and operational boundaries

Docker Desktop showed an AF_UNIX endpoint startup error earlier. Engine API calls
subsequently succeeded, while Desktop status remained `stopped`. No socket
directories or Docker settings were changed. This task does not claim that the
Desktop startup issue is permanently resolved.

Initialization scripts run only on an empty volume. A failed initial setup needs
diagnosis, not automatic volume deletion. Password file changes do not rotate
existing PostgreSQL role passwords. Never run `down --volumes`, prune, or restore
against an existing volume without explicit authorization. A cloud host has not
been provisioned or exercised by this task.

## Verification results

Completed on 2026-10-14 with Windows, Docker Desktop 4.85.0, Compose 5.3.1,
PostgreSQL 18.6 (Linux amd64), and Python 3.12.14.

- Fresh `acoa-dev` container, dedicated volume and internal network: created,
  healthy, correct project ownership, no host port on the base configuration.
- Both Compose configurations: parsed successfully. The optional local overlay
  required a separate project-scoped NAT bridge; publishing from the internal-only
  network did not provide Windows host access here. The revised overlay bound only
  `127.0.0.1:15432`, and an IPv4 TCP connection from the host succeeded. The base
  was reapplied afterwards: healthy, no published ports, internal network only.
- Migration and app passwords: authenticated via TCP/SCRAM inside the dedicated
  container. An incorrect app password was rejected with psql connection status 2.
- Migration-owned synthetic table and identity sequence: created successfully;
  application INSERT/SELECT/UPDATE/DELETE succeeded through default grants.
  Application DDL in both `acoa` and `public`, and `SET ROLE acoa_migrator`, were
  rejected with `insufficient_privilege`. Administrative, CREATE/TEMP, and migration
  membership privileges were absent.
- Transaction rollback and service restart: the single committed synthetic row
  remained; the rolled-back row did not. The probe table was then dropped by the
  migration role; the `acoa` schema contains zero business/test tables afterwards.
  Container recreation for the overlay also preserved the initialized roles/schema.
- Password preparation: three distinct random files, repeated setup created zero
  additional files and retained the same file bytes. Git ignores all three actual
  password paths. Password values were not printed or committed.
- Existing Python checks: **98 tests passed**, Ruff check and format passed,
  strict mypy passed for the existing four source files and the preparation script,
  and pip dependency consistency passed. No tests or dependency declarations were
  added or modified.

Two verification-command issues were corrected without project-data loss: a
PowerShell pipe added CR to a shell script's final line after successful SQL checks,
and an unsupported Docker negative-label filter prevented an inventory comparison.
Neither was treated as a database failure or a passing inventory check.

The pre-existing unrelated container ID remained present, but changed from exited
to running during verification. Its restart policy is `no`; the source of that
state change was not established. Commands issued here targeted only the new ACOA
service/resources, but unchanged state of other containers is not claimed.

Docker Desktop later reported `running`. No factory reset, socket rename, Desktop
setting change, diagnostics upload, or unrelated container stop was performed.
Desktop restart reliability and the original socket error's permanent resolution
remain unverified. Cloud/other OS/architecture deployment, host-side SQL login,
backup/restore, business migrations, and application database adapters were not
exercised. Starting this service grants no live employer-action authority.
