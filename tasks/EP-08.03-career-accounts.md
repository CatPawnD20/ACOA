# EP-08.03 — Authorized career-account creation

## Scope and requirement links

This task implements the provider-neutral account-creation path for `F-08.01`,
`F-08.02`, `F-08.05`, `F-08.06`, `F-08.07`, `E-04.02`, `E-07.01`, `E-07.03`,
`P-07`, `P-17`, `P-19`, `ADR-006`, `ADR-007` and `ADR-012`. It uses no real
identity, credential, career site or external account.

## Delivered behavior

- An immutable account plan binds one logical account to the exact task, application,
  trusted HTTPS origin, browser permit, provider, login digest, terms digest, allowed
  data categories and finite lifetime. Its semantic key fences the same logical
  account/provider pair across application attempts.
- Account creation is now a supported prepared external action. It still passes through
  the existing `prepare → reserve → execute once` Policy/Budget Gate protocol and a
  trusted adapter registered with `ExternalActionExecutor`; browser or generated code
  receives no independent submission method.
- The executor adapter reloads the exact plan and caller-injected private login material,
  verifies their digest and every prepared-action binding, creates a 256-bit random
  URL-safe password and writes the credential to an injected secret store before the
  one permitted provider call. Login and password fields are excluded from object
  representations and PostgreSQL.
- Provider results distinguish `created`, `waiting_user`, `failed` and `unconfirmed`.
  CAPTCHA, MFA, additional-data requests, binding terms and access denial are explicit
  obstacles. They are recorded for handoff and never trigger bypass or an automatic
  retry. Exceptions and malformed provider results become `unconfirmed`.
- Account creation no longer mutates an application's submission state or opens an
  “unknown submission” incident. Submission reconciliation rejects account attempts;
  the dedicated account event remains their outcome evidence.
- PostgreSQL stores append-only plans and one outcome per external-action attempt. It
  retains only login/provider hashes and a unique opaque secret-reference UUID. Unique
  account identity by origin/login digest prevents a second logical account record.

## Verification

Verified locally on 2026-10-16 with synthetic `.invalid` identity material:

- A transient central-executor probe made exactly one provider call, persisted one
  secret reference and one created event, and returned a provider acknowledgement. The
  credential representation exposed neither login nor password.
- A second provider result containing both MFA and CAPTCHA produced a `waiting_user`
  event, no acknowledgement and a conservative unconfirmed attempt result. No bypass,
  retry or real external I/O occurred.
- Migration `0022_career_accounts` passed graph/history/offline-SQL validation and was
  applied to the dedicated development database. A rollback-only probe using the real
  `acoa_app` role round-tripped a plan/event and verified `SELECT,INSERT` with no
  `UPDATE,DELETE` privilege; no synthetic rows remained.
- The final gate covers the existing test suite, Ruff formatting/linting, strict mypy,
  dependency consistency, approved-document preservation and the active checksum
  manifest. No test, fixture, mock or testing utility was added or modified.

## Remaining boundaries

A deployment must inject a real OS keyring or managed encrypted secret store and a
trusted provider adapter before account creation can run. Neither is discovered from
environment files or bundled here. EP-08.04 owns synthetic-site form submission,
timeout ambiguity and reconciliation; EP-08.05 owns optional AI-guided browser work.
