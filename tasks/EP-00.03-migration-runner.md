# EP-00.03 Follow-up — G0 Migration Runner

## Objective and scope

Complete the missing L4 G0 migration-infrastructure prerequisite without business
schema revisions. Trace: L4 section 7/12, EP-00.03; E-05/E-07/E-11;
ADR-002/011/013. The user authorized continuation on 2026-10-14.

No tests, fixtures, mocks, or test utilities are added or modified. Existing
checks and direct runtime probes verify the behavior. No employer actions,
application adapter, API, remote push, cloud deployment, or business schema is
implemented. Approved L0–L4 specification bytes remain unchanged.

## Work units and acceptance

1. Install explicitly pinned migration tooling separately from the base Python
   package contract. Add Alembic configuration, an empty revision directory, and
   online/offline execution using thin orchestration and named operations.
2. Require an explicit password file and fixed `acoa` database / `acoa_migrator`
   role. Before online execution validate database/user, schema owners, absence of
   cluster-admin privileges, and absence of app access to migration metadata.
   Fail without revealing credential values or driver exceptions.
3. Keep Alembic's version table in `acoa_migrations`, owned by the migration role
   and inaccessible to the app role. Update fresh-volume initialization and apply
   only that schema addition to the verified existing ACOA development database.
4. Provide a one-shot Compose maintenance service on the internal database
   network with only the migration password mounted. Normal `up` does not start
   it. Exclude secrets/private files from its build context.
5. Verify Windows host and Linux container online commands, repeated upgrade,
   restart persistence, metadata privileges, controlled failure paths and offline
   execution. Include tooling/offline checks in CI and audit the new dependencies.
   Restore the default unpublished database port before delivery and commit.

## Design and operational boundaries

`deployment/migration-requirements.txt` pins SQLAlchemy 2.1.4, Alembic 1.20.0 and
psycopg[binary] 3.3.6. The current `acoa` package still has no declared runtime
dependencies; importing it does not initiate migration or connection work.
Migration tools are installed explicitly for maintenance and CI.

The runner never discovers `.env` files or connection URLs. It accepts an explicit
host/port and password-file path, constructs the driver URL structurally, and
redacts controlled errors. The database/user are not caller-selectable. Fixed names
and owner checks are a guard against wrong targets, not proof of ownership of an
arbitrary remote server; select only your dedicated ACOA deployment. The Compose
service selects the dedicated internal service name directly.

One outer transaction owns each online command. Alembic uses the validated
connection, and resources are disposed on success or failure. There is no automatic
retry. Autocommit/nontransactional future revisions need separate review; no
concurrency/locking guarantee for simultaneous future migrations is claimed.
Only `current`, `upgrade head`, `heads`, `history`, and offline `upgrade --sql` are
exposed. Revision authoring, downgrade, autogeneration and business schema
revisions remain outside this bootstrap scope.

The maintenance container uses a digest-pinned Python base, immutable filesystem,
temporary filesystem, no Linux capabilities, no-new-privileges, bounded CPU/memory,
and only the ACOA internal network at execution. Its dependency download happens
during image build without credentials. It has no application/admin password,
database data volume, Docker socket, host workspace mount, or external-action
secrets. Its container process runs as root with these boundaries; Docker secrets
are file mounts and Docker administrators remain trusted. This is an operations
tool, not an AI-generated-code sandbox or a production hardening claim.

The application still owns no business tables. A successful empty `upgrade head`
creates only an empty `acoa_migrations.alembic_version` table. Application object
grants remain limited to objects created by `acoa_migrator` in schema `acoa`.

Official references: [Alembic environment](https://alembic.sqlalchemy.org/en/latest/tutorial.html),
[connection sharing](https://alembic.sqlalchemy.org/en/latest/cookbook.html),
[offline SQL](https://alembic.sqlalchemy.org/en/latest/offline.html), and
[SQLAlchemy URLs](https://docs.sqlalchemy.org/en/21/core/engines.html).

## Verification results

Verified on 2026-10-14 with Python 3.12.14, PostgreSQL 18.6, Windows host execution
and the Linux amd64 maintenance image:

- Windows host TCP: `current`, repeated empty `upgrade head`, and commands after
  a PostgreSQL service restart succeeded. `heads`, `history`, and offline SQL also
  succeeded. The real dedicated development credential file was read only for the
  explicitly authorized connection checks; no value was printed or committed.
- Linux maintenance service: image build, `current`, repeated `upgrade`, `heads`,
  `history`, and offline SQL passed with its read-only filesystem and restricted
  privileges. Only the migration password was mounted; admin/app password files
  and a local secret directory were absent. The final image build context was
  approximately 8.8 kB and included only allowlisted migration inputs.
- Database state: only an empty `acoa_migrations.alembic_version` table exists;
  its owner is `acoa_migrator`. Schema `acoa` has zero business tables. Application
  reads/inserts against the version table were rejected by PostgreSQL. The metadata
  survived restart and repeated upgrades without a fabricated revision.
- Controlled failures: missing password argument, nonexistent file, invalid port,
  and an incorrect role password returned exit code 1 with value-free diagnostics.
  An authenticated application-role connection was rejected by target validation.
  A temporary metadata-schema grant inside a transaction was rejected before
  Alembic execution; the transaction was rolled back and normal validation passed.
- Offline effect guard: SQL generation opened no sockets, performed no DNS or
  subprocess work, and did not read the migration credential file. SQLAlchemy's
  harmless local `socket.gethostname` call during Windows platform detection was
  permitted; the first overly broad audit guard incorrectly classified that as
  network work and was corrected without changing runtime security settings.
- Existing checks: **98 tests passed on Windows and 98 on clean Linux source**;
  Ruff check/format, strict mypy for four existing files plus three deployment
  scripts, pip consistency, and actionlint's built-in workflow validation passed.
  No tests or base package dependency declarations changed.
- Dependency auditing: both the Windows environment and Linux migration-image
  package inventories reported no known vulnerabilities using pip-audit 2.10.1.
- Final base service: healthy, on its own internal network, with no host port
  published. One-shot maintenance and verification containers were removed by
  `--rm`. No other project's database or credentials were selected.

All runner functions and orchestration boundaries were reviewed, with separate
identity, schema-ownership, privilege, credential-reading, URL construction and
connection/transaction responsibilities. Approved-document hashes, active hashes,
local links, and the staged diff are checked before a focused local commit.

This completes the missing migration-runner prerequisite in the local G0 evidence.
It does not establish that GitHub-hosted CI or a cloud deployment has passed.
There are no business revisions, so upgrade/downgrade recovery for real schema
changes, autogeneration, concurrent migration locking and backup/restore remain
unexercised. Fresh-volume schema addition was applied directly to the verified
existing development database; the whole initializer was not rerun on that volume.
Normal/failure paths and metadata persistence were exercised, but no complete
new-volume initialization was repeated during this follow-up. Dry-run and disabled
external-action defaults remain unchanged.
